# 日志系统

**适用场景**: 需要将结构化事件渲染为玩家可读日志或调试输出时.

## 日志目标

- 让开发者通过文本判断基础玩法是否有趣.
- 解释事件因果, 不只输出数字.
- 保留黑色幽默语调, 但不掩盖结构化事实.

## 渲染流程

1. 收集当前 Tick 事件.
2. 按 severity 和事件顺序排序.
3. 合并低优先级重复事件.
4. 按 event_type 匹配模板.
5. 查实体显示名并插值 payload.
6. 输出玩家日志和调试日志.

## 模板示例

```text
【第{tick}天】{actor}趁乱偷走{target}的{amount}两银子, 却把自己的欠条落在{territory}。
【第{tick}天】{winner}攻下{territory}, {loser}折损{casualties}人, 江湖传言此战全靠一包误撒的石灰粉。
```

## 优先级策略

| severity | 展示策略 |
|----------|----------|
| critical | 必定展示, 不合并 |
| major | 默认展示, 同类过多时摘要 |
| normal | 可合并为 Tick 摘要 |
| minor | 默认进入调试日志和指标 |

## 可读性约束

- 每条玩家日志尽量一到两句.
- 同一 Tick 不输出过多流水账.
- 重要实体显示名称必须稳定.
- 黑色幽默来自反差和后果, 不使用无因果的随机笑话.

## 失败处理

- 模板缺失时输出结构化 fallback, 并记录开发错误.
- 渲染失败不能丢失事件.
- 日志测试可断言包含关键实体名和数值, 不断言全句完全一致.
